# burrow audit — 2026-11-22

Second full audit, at HEAD c37d6dc ("polish clean preview sorting and alignment",
#17), one audit cycle after docs/audit-2026-10-31.md drove PRs #16 and #17.
The owner's question this time is narrower: the goal is "a clear view into files
that are taking up space / are cruft in my workspace that I could clean up," it
is closer than when we started, but it still feels too complicated. Method: four
parallel codebase deep-dives (engine/action/safe, catalog, cli/tui, and the
support packages), plus hands-on runs of the built binary on this machine
(Fedora 45, dnf, 1.48 TiB home, 12M files).

## Verdict

The October fixes landed. Not mostly — comprehensively: every structural
finding from the last audit that was marked "fix" is fixed and most are pinned
by tests. The architecture is no longer the problem. What remains is three
thin layers:

1. **The tool speaks in labels instead of evidence.** Rows carry five
   vocabularies (contract, regen cost, risk, tri-state mark, active flag) with
   no legend anywhere; the one field designed to explain a row to the user
   (Target.Evidence) is populated by the catalog and rendered by nothing; and
   the regen-cost labels are a hardcoded snapshot of one person's toolchain
   biases — npm cache "cheap," Go module cache "expensive," which is exactly
   backwards on the machine this tool runs on (see A1; the owner noticed this
   unprompted).
2. **A second layer of dead surface.** The October cleanup removed the fossil
   layer (spec citations, dead keys, dead flags); the engine still carries a
   fresh one it grew itself — a mandatory Describe() method with zero callers,
   a double status channel where half of every outcome is computed and
   discarded, six write-only fields, a decorative error return.
3. **A short list of real correctness gaps** — none catastrophic, all cheap:
   items trashed on other mounts are silently unrestorable, journal append
   errors are discarded (fail-open on the undo trail), df is hardcoded to /,
   dev.docker-buildx and containers.docker-build-cache can both run on the
   same bytes, a malformed journal line bricks history, and two different runs
   on this machine share one printed short id.

The mark — "clear view, then clean" — is now two features that each work:
analyze answers "where did it go" (measured below: 26 s for a 1.48 TiB home,
honest partial status with the reason on stderr and in JSON), and clean answers
"what can I safely remove." What is missing between them is not another
feature; it is legibility: say what each row is, why it is checked or not, and
stop making the user decode the model.

## A. The product model: labels, evidence, and the regen-cost problem

### A1. Regen cost is a hardcoded opinion, and the cost × activity policy is backwards

The user's complaint, verified in code: internal/catalog/dev/dev.go:287-299 is
a second id-keyed switch parallel to itemSpecs — go-mod, rust-registry,
rustup, conda, nix are "expensive"; npm, pnpm, bun, pip, uv, poetry are
"cheap". On this machine that renders as:

```
[ ] npm cache      50.9 GiB  [owner] cheap        low
[ ] Go module cache 7.2 GiB  [owner] expensive    low
```

The owner primarily builds a TS app. npm cache is their hottest, most
regeneration-costly cache — 50.9 GiB of downloaded tarballs that cost real
time to rebuild — and it is labeled cheap and pre-selectable, while a Go module
cache they have not touched in months is labeled expensive and is the hardest
row in the catalog to select (expensive rows are excluded even from bulk
selection after explicit opt-in; dev_test.go:567 pins this).

Two distinct flaws stacked:

- Cost is workflow-relative and this table hardcodes one workflow. Nothing
  derives it from observed signals, even though the evidence already exists —
  the same mtime probe that produces the ,active marker knows which caches a
  person actually uses.
- The cost × activity combination is applied backwards. "Expensive to
  regenerate" only matters if you are about to regenerate it, i.e. when the
  cache is active. An idle expensive cache (this go-mod) is the safest,
  highest-value target in the catalog: you were not going to pay the cost
  anyway. The current policy treats expensive as a permanent veto instead of a
  rating that only binds when active. The correct rule is roughly:
  active → off regardless of cost; idle+cheap → on; idle+expensive → on or one
  keystroke away, not walled off.

Related fragility: regenFor silently defaults any unknown id to RegenFree
(cheap-to-preselect) — add a dev cache without a regen entry and it becomes
pre-selectable. The table test pins CacheRoots but not the regen column.

Fix, in order of preference: (1) collapse cost to what it actually gates —
merge the regen column into itemSpecs where the policy lives, and let the idle
gate own the activity dimension; (2) if cost survives as a concept, derive it
from presence-of-toolchain plus observed activity rather than a static table;
(3) at minimum, pin every id's regen in the table test.

### A2. The headline and the category header disagree, and neither says what it counts

Full-catalog plain output, two lines apart:

```
Reclaimable now: 6.6 GiB across 7 items
▸ Projects  2.1 GiB / 29 items
```

The first number is the pre-selected default set (what runs if you hit enter on
the review). The second is the sum of candidate rows only. Both are honest;
neither is labeled, and the juxtaposition trains distrust — the October audit
flagged this shape ("User cache 239.0 GiB" next to "Selected: 6.5 GiB") and
the fix introduced a new instance of it. One line of copy fixes it:
"Reclaimable now: 6.6 GiB pre-selected (169 GiB shown)". See also A7.

### A3. Row vocabulary with no legend

One clean-preview row carries: the [x]/[~]/[ ] tri-state (still unexplained
anywhere — selectionMark, tui/clean.go:1091-1110, absent from both help
views), size, [trash]/[owner] contract, regen cost with the ,active suffix,
and risk. That is five vocabularies; the only decoder is user-guide.md:60-74,
which is itself stale (it says "n clears"; the code binds N for none and n for
sort-name, clean.go:1211-1212). K (whitelist-keep) remains a one-keystroke
file write with no undo hint — feedback is one status line "kept N path(s)".
The fix is not fewer concepts; it is a legend line in the help overlay and a
plain-language reason on the row — which A4 makes nearly free.

### A4. Target.Evidence — the explain-why field nobody renders

catalog/system populates Target.Evidence at six sites (system.go:106, 126,
153, 175, 208, 245) for exactly the purpose the product needs — say why this
item exists — and neither the TUI, the plain renderer, nor the JSON emits it
(cleanItemJSON has no evidence field, cli/clean.go:456-475). It is dead weight
in the one place the product is still too complicated. Render it (a dim
second line under the row, and an "evidence" JSON key) or delete the field;
rendering it is the cheapest large legibility win available.

### A5. Group names collide

Two distinct repos both render as a group titled "logiops"
(~/Projects/brandtg/config/files/logitech/logiops and
~/Projects/dotfiles/logiops) — verified via JSON group_title. Plain output
also shows "dist" nineteen times across repos. In the TUI the group hierarchy
carries the path; in --plain the identical titles are indistinguishable.
Disambiguate on collision (append a distinguishing path segment), as git
short-hash display does.

### A6. The biggest number on this machine is invisible to clean by policy

analyze ~ finds: Projects 598 GiB (of which one work repo, greg-wisy-ai, is
421 GiB), .cache 371 GiB, Documents 274 GiB. The clean Projects category
reports 2.1 GiB — correct, because artifacts of repos committed within
[projects] active_within are "kept" (excluded from candidates entirely), and
the big repos are active. The policy is right; the consequence is that the
bulk of the machine's real footprint — hundreds of GiB of rebuildable
artifacts inside active repos — appears nowhere in the clean flow, and the
user must navigate analyze by hand to learn it. A one-line "kept by policy:
N GiB across M artifacts in active repos" per category (computable during
discover; the data is already in hand when an artifact is rejected) would
close the view gap without changing any decision the tool makes.

### A7. Smaller surface notes

- uv cache 88.8 GiB — the single largest reclaimable item on this machine —
  renders "cheap,active" and off. Correct (it is in use), but nothing
  distinguishes "88.8 GiB, one keystroke away" from a 100 MiB row. Sort or
  shade by size within groups; the data is on the row.
- The [R] marker fires for every row inside a reclaimable root (WithinRoot,
  tui/analyze.go:157-158), so deep .cache navigation is a wall of [R].
  Restrict the marker to the root row itself; keep the hint there.
- The review screen largely restates the preview's selected rows in argv form
  — three surfaces (preview → review → summary) where a single confirm with
  expandable argv would carry the same safety with one less context switch.

## B. Correctness gaps (real, ranked)

1. **Cross-mount trash is silently unrestorable.** Put creates per-mount
   trashes (trash/trash.go:57-88) but List reads only the home trash
   (trash.go:149-151), so history --restore — the entire undo story — cannot
   see items trashed from another filesystem. Unchanged from the October
   audit's "known gaps" note; it remains the highest-value fix in these
   packages. Also: Restore uses context.Background() (trash.go:202), so a
   cross-device restore of a multi-GiB item is uncancellable — the exact bug
   fixed for Put, left on the restore path.
2. **Journal append errors are discarded.** _ = jw.Append at
   engine/pipeline.go:446, 475, 581. The journal is what history --restore
   reads; a failed write silently loses recovery data. Fail closed instead:
   surface the error in the run summary (and skip the mutation, or at minimum
   mark the run unrestorable).
3. **FreeBytes is hardcoded to "/"** (pipeline.go:453, 469; cli/clean.go:439).
   On a machine with a separate /home the df headline and freed-bytes deltas
   are wrong or move backwards. Stat the common parent of the run's targets.
4. **docker-buildx double-count.** dev.docker-buildx trashes
   ~/.docker/buildx/cache (dev.go:232-234) while
   containers.docker-build-cache runs docker builder prune -f — the same
   conceptual bytes as two rows in one plan, both executable; selected totals
   double-count. containers already has a Reconciler; dev has none. Either
   give dev a reconcile rule or drop the dev row.
5. **A malformed journal line bricks history.** journal.Read errors on the
   first bad line and returns a partial list (journal.go:192-195); a truncated
   final line (crash mid-append) makes burrow history unusable until the file
   is hand-edited. Skip or ring-fence a bad trailing line.
6. **short ids collide.** Observed live: runs 01M5P6W7N9Y2QVFEJ5ZETAMETA and
   01M5P6W7Q88YXZVKG720KPMG10 both print as 01M5P6W7 in the history table.
   Prefix matching would refuse a restore by that id as ambiguous (good), but
   the table shows two different runs under one id. Lengthen until unique
   among listed runs, git-style.
7. **--min-size passes unknown-size items** (includeTarget only applies the
   floor when SizeKnown, pipeline.go:365). Untested and undocumented; a
   --min-size 1G run still offers every unmeasurable row.
8. **Exit-code seams.** The root-without-SUDO_USER refusal exits 2 on
   clean/bare (mapped to ExitUsage) but 1 on history/analyze/config/purge
   (raw error) — same mistake, two codes. Quitting the TUI with q exits 0,
   indistinguishable from a successful no-op run.
9. **--plain on analyze prints JSON** (analyze.go:127-129). The flag help says
   "non-interactive plain-text output"; there is no plain-text analyze
   renderer. Make the name and behavior agree one way or the other.
10. **Scoped-but-empty --only is silent.** The "no category matched --only"
    warning fires only on the unscoped path (pipeline.go:272-274); a scoped
    run that filters everything out says nothing.
11. **Same-inode mutation is undetected.** Snapshot.Matches compares only
    dev/ino of target and parent (identity.go:63-76) while Snapshot.Size/Mode
    sit captured-but-unused; an in-place rewrite is invisible to the guard.

## C. Dead surface, round two (verified zero production callers)

Engine/action/safe:

- Action.Describe (types.go:137) — mandatory interface method, zero callers
  anywhere including tests. Delete from the interface.
- The double status channel: every Action reports via both Result.Status/Reason
  and error; executeItem recomputes status purely from the error
  (pipeline.go:489-544) and the one production progress consumer ignores
  Result entirely (cli/clean.go:211). Collapsing to one channel deletes the
  skip() helper, errString(), and half of each Run body — the largest single
  complexity reduction available in internal/action.
- Write-only fields: PlannedItem.GuardStop and .TimedOut (pipeline.go:29;
  sum.GuardStops/sum.Timeouts are the consumed values), Summary.Command,
  Snapshot.Size/Mode (see B11), Target.Evidence (see A4 — render or delete).
- Env.Trash (env.go:130), safe.State.String (guard.go:16), safe.ErrUnsafe and
  Violation.Is (validate.go:21-34, test-only), Options.DiscoverTimeout (a knob
  no caller turns), Build's always-nil error return (pipeline.go:275) and the
  dead fatal branch at cli/clean.go:98-100. engine.Measure and TotalsOf are
  exported with only internal callers.

Support:

- trash.Put (trash.go:92-94) — tests-only; switch tests to PutContext, delete.
- whitelist Set.Entries() — tests-only.
- owner.Runner.Log — never assigned in production; a dead knob on a
  safety-critical type. Wire it or delete it.
- owner/commands_test.go retiredCtors names constructors that no longer exist.
- catalog Registry.ByID (catalog.go:36) — still dead.
- usercache.go:180-183 second TrashDir fallback — config.ResolvePaths always
  sets it; dead defensive duplication.
- engine/measure.go:98-104 diskUsage is a byte-for-byte copy of
  internal/disk.Blocks512 — the AGENTS.md one-helper rule names this exact
  case; engine can import disk without a cycle.

Layering nits: scan imports owner for one constant (TimeoutScanPerRoot) — the
duration belongs in a leaf package; logrus is a direct dependency whose only
job is muting gdu's own logging (scan.go:215-219).

## D. Structure notes (cost, not bugs)

- **Measure is parallel within a category, serial across them.** The
  per-category loop calls Measure inside the sequential planning loop
  (pipeline.go:230-246), so dev/user-cache/downloads sizing happens
  back-to-back per category. One Measure call over the union of targets is
  both simpler and faster; the loop's shape, not the engine, is what costs.
- **Progress fires in a burst.** Options.Progress is called after wg.Wait()
  (pipeline.go:223-240), so all "category discovered" lines land at once after
  discovery completes; the comment at cli/clean.go:267-268 claims incremental.
  During Measure — many 30 s-capped du forks — there is no feedback at all.
  The deterministic-order design is defensible; the comment and the gap are
  not. An ordered printer called from the goroutines is a small change.
- **analyze and clean walk the same trees twice with two engines** (gdu vs
  per-target du). Architectural today; noting it because it is the remaining
  structural latency after D1, not a recommendation to couple them.
- **gdu's dependency baggage** (badger, ristretto, modernc sqlite, tview,
  tcell, xz, flatbuffers, otel) is compiled into the static binary for
  analyzers burrow never uses — accepted and documented in AGENTS.md; still
  the largest dependency-complexity item.
- **Hooks machinery** (Reconciler + Warner + double ApplyHooks + idempotence
  flag) serves exactly three implementations. A plain function list would read
  the same; fine to leave, not fine to extend the pattern.
- **Flag surface: 26 unique names for a two-command product.** Selection
  flags are defined three times (root, clean, purge) and --age likewise; the
  persistent --plain/--yes/--dry-run/--color are silently accepted and ignored
  by history/config/version. Consolidate definitions; make no-op persistence
  a usage error.
- **desktop-pkgs is default-on with the worst machinery-per-byte ratio** (314
  lines, orphan-user-data re-check guards, snap revision validation) and
  delivered 8 KiB + one flatpak row on this machine. Demote from
  default_categories; keep the code. The 8 frontend-cache rows in dev exist
  mainly to feed user-cache's exclusion list — policy indirection buying
  little; fold them into user-cache.
- **docker system df parsing keys on the first all-digit column and label
  strings** (containers.go:219-233) — fails soft to unknown, but a docker
  output change silently blinds the category's sizes. The bespoke
  /proc docker-build scan (containers.go:263-288) burns a full /proc walk per
  discovery for one evidence line.

## F. Tests and gate

- make gate FAILED on govulncheck: GO-2026-6865 (klauspost/compress v1.18.1,
  fixed in v1.20.2 — trace enters via gdu's init in scan.go:216) and
  GO-2026-6859 (stdlib net/http @go1.26.10, fixed in go1.26.11). Both traces
  are init/indirect paths, so practical severity for a local CLI is low, but
  the gate is red and CI runs gate-strict. Fix: go get
  github.com/klauspost/compress@v1.20.2 and bump the toolchain. Everything
  else in the gate passed (fmt, vet, tests, safety gate, man-page freshness,
  static binary).
- Gaps: engine.Measure has no unit tests at all (du parsing, kb conversion,
  timeout-to-unknown, worker cap, cancellation — all untested; the file is
  ~100 lines and easy to test). catalog/roots has zero tests despite carrying
  the [R] bridge's most-specific-root rule. Unpinned: estimate-freed
  precedence (action bytes vs measured size, pipeline.go:548-556),
  --min-size × unknown-size, scoped-but-empty warning.
- Strengths worth keeping as the template: the AST-enforced owner argv table,
  the probe-category scoping proofs, the swap-simulation identity tests,
  dev's CacheRoots pin, projects' real-git fixtures.

### What not to change

The trash-only delete model, journal + restore, exact-argv owner discipline,
the itemSpecs table, collapsed distro adapters, gdu containment with the du
repair path, fail-closed guards, and the config schema. The October verdict
stands and strengthens: the safety architecture is the differentiator and is
now also the best-tested part of the codebase. The distance to the mark is
legibility and a short correctness list — none of it architectural.
