# burrow audit — 2026-10-31

Deep-dive review of the repo at HEAD 72a8b1f ("trash is the only delete path, purge
a clean category", PR #15). Question asked: why does burrow feel clunky and
unpolished next to Mole, and what would fix it. Method: full read of cli/tui/
engine/catalog/docs, three parallel codebase audits, plus hands-on runs of the
built binary on the dev machine (Fedora 44, dnf, large home dir).

## Verdict

The safety architecture is genuinely good and should not be touched. The
"clunky" feeling is three separate problems wearing one coat:

1. **Latency without feedback.** Every entry point pays 14–47 seconds of silent,
   un-parallelized work before showing anything, and even a scoped run scans the
   whole catalog. Mole feels instant because it shows you something while it
   works; burrow feels frozen because it shows you nothing until it's done.
2. **The product is two half-bridged apps.** `clean`'s preview and `analyze`'s
   explorer are separate TUIs with different keymaps, different vocabularies,
   and a dead one-way bridge between them (the `[R]` reclaimable marker is
   wired in the renderer but no caller ever populates it). The "one flow" pitch
   in the README breaks the moment the user asks "why is this dir big — and can
   burrow clean it?"
3. **Fossil accretion.** PR #15 deleted the spec, the plans, the status doc, and
   the static safety gate, but ~50 `spec §N` comment citations, a stale
   AGENTS.md, dead config keys, dead flags, dead exported helpers, and a
   deprecated command (`purge`) with a unique flag (`--age`) all survived. A
   lot of what reads as "unpolished" is code and docs describing a product that
   no longer exists.

None of these need a redesign. Each is a focused sweep. Ranked fixes are at the
bottom.

## What I measured (hands-on, this machine)

| Run | Time | Notes |
|---|---|---|
| `burrow --dry-run --plain` (full catalog) | **47.2 s** to first byte of preview | 47 s of complete silence, no spinner, no "scanning" line |
| `burrow --dry-run --plain --only projects` | 14.4 s | same as… |
| `burrow --dry-run --plain --only dev` | 13.9 s | …every other category, even… |
| `burrow --dry-run --plain --only downloads` | 13.8 s | …`downloads` and `containers`, which found nothing |
| `burrow analyze ~ --json` | **43.0 s**, `scan_status: "partial"` | fixed 90 s deadline, no live tree, "partial" with no reason shown |

So `--only` saves nothing: **it filters items after discovering and measuring
the entire catalog** (engine/pipeline.go:260 applies `--only` per item; the
comment above `categoryIncluded` says so explicitly). The constant ~14 s floor
on every invocation is the full-catalog discover phase; the extra ~33 s in the
full run is the fully-serial `Measure` phase on top (see "Scan latency" below;
the first run was also cold-cache, later repeats of the full run will land
nearer 14–20 s — the floor itself is the constant).

The 146-line plain preview also showed the surface problems concretely:
- The `Projects` category renders a group also titled `Projects` (the literal
  `~/Projects/Projects` dir) — `▸ Projects … ▸ Projects` reads like a bug.
- A group (`snoopy  116.0 KiB / 5 items`) prints with a count but zero item
  rows — group item-count and rendered target rows disagree after filtering.
- Missing categories vanish entirely: no System, no Downloads, no Containers
  rows at all, so "nothing found", "not applicable to this distro", and
  "discovery timed out" are all indistinguishable from "not scanned".
- `1 items` pluralization, no column headers over the regen/risk columns,
  and a `User cache` header claiming 239.0 GiB when the honest headline is the
  6.5 GiB at the bottom.

## A. Flow and latency (the biggest feel problem)

### A1. Silent scan before every screen
- `clean`: `engine.Build` runs fully synchronously before the TUI opens
  (cli/clean.go:69–76). No spinner, no progress, no "discovering…". Compare
  `analyze`, which scans in the background precisely so it can render progress
  (cli/analyze.go:138–141). The main command is worse than the secondary one.
- Any discovery warnings are printed to stderr *before* the alt-screen opens
  (clean.go:82–84) and are therefore invisible until after you quit — on a
  terminal nobody ever sees why the projects scan timed out.
- After confirming, the TUI quits, the screen blanks back to the shell, and
  `engine.Execute` runs elevated apt/dnf/docker commands **with no per-item
  feedback at all** until `RenderSummary` appears at the end
  (tui/clean.go:415–421, clean.go:135).

### A2. Measurement is serial `du` forking
`Measure` (engine/measure.go:17–28) forks one `du -sk` per directory target,
sequentially (measure.go:41), called per-category inside the planning loop
(pipeline.go:218). `user-cache` produces one target per top-level `$XDG_CACHE`
entry — this machine has 277 items there — so the preview waits on hundreds of
back-to-back `du` processes. Discovery is already parallel
(pipeline.go:172–196); measurement was left behind. Parallelizing `Measure`
(errgroup, bounded) or folding measurement into the discover goroutines is the
single best feel-per-dollar change in the codebase.

### A3. `--only` doesn't scope the work
As measured above: `--only` is a post-hoc item filter (pipeline.go:260). A
user typing `burrow --only dev` to "just check npm" pays for walking every
project root and every cache dir. Either resolve selectors to a category set
before discover (fast path) or document nothing — because the right fix is
obvious: run discovery only for categories that can match the selectors, and
keep item-level matching within those.

### A4. The analyze scan is all-or-nothing and capped
`scan.Analyze` (internal/scan/scan.go) builds the complete gdu tree, deep-copies
it into its own `Node` model (scan.go:244–273, doubling peak memory), then hands
the finished tree to the TUI. Consequences:
- Nothing renders until the whole scan finishes (ncdu-style live navigation is
  impossible by construction; the internals audit confirms the current
  containment design forbids retaining gdu's live tree).
- A fixed 90 s deadline (owner.TimeoutScanPerRoot, scan.go:141) with no config
  or CLI override makes big trees silently `partial` — this machine's home scan
  *is* partial, and the reason isn't surfaced in the JSON's headline field.
- `applySharedExtents` (extents.go:58) re-opens every file with FIEMAP on
  reflink filesystems, roughly doubling scan time where it runs.

## B. The two TUIs don't speak the same language

Same app, two keymaps that actively betray muscle memory (tui/analyze.go:644–658
vs tui/clean.go:939–959):

| Key | analyze | clean |
|---|---|---|
| `enter` | enter directory | open review |
| `→/l` | enter directory | expand group |
| `←/h` | parent dir | collapse group |
| `n` | sort by name | select none |
| `space` | nothing | toggle row |
| `a` | nothing | select all safe |

Also:
- **Hidden keys everywhere.** analyze's short help shows only 7 of ~11 bindings
  — `n`, `t`, `c` are invisible unless you find `?` (analyze.go:660–662).
  clean's footer hides `n`, expand/collapse, and `g/G` (clean.go:962–964).
- **`q` closes the help overlay instead of quitting** in both models
  (analyze.go:270–275, clean.go:440–445), so the first `q` after `?` never
  quits. One-line fix each.
- **Sorting by mtime (`t`) in analyze sorts by a column that is never
  displayed** (analyze.go:544–571 renders no mtime).
- **The `[R]` reclaimable marker is dead.** The analyze renderer reserves 4
  columns for it (analyze.go:549–552) but `cli/analyze.go:136–145` never
  populates `CategoryRoots` — grep confirms no production caller exists. This
  was the killer feature (spot a big dir, see it's cleanable, jump to clean)
  and it's wired-but-off.
- **No current-directory total in the analyze header** (analyze.go:478–501);
  you can't see "this dir = X" without going up a level. No percentage of
  parent either (ncdu shows both). No mouse in either model. No PageUp/Down or
  `g/G` in analyze while clean has them.
- **The clean review screen cannot scroll** (clean.go:465–476: only
  enter/esc/q). On a 24-row terminal a moderate selection overflows with no
  way to see the top or bottom, and the "Review — these exact commands will
  run." footer is unstyled and drops the platform header.
- `K` (whitelist-keep) is fire-and-forget: one keystroke writes N paths to the
  whitelist file, no confirm, no undo hint (clean.go:654–700); if the
  whitelist failed to load earlier the manager is nil and `K` just says
  "whitelist unavailable" (clean.go:678–680, cli/clean.go:172–181).
- Collapse state and the filter interact invisibly (clean.go:745,756:
  collapsed groups auto-expand only while the query is empty); the
  `[x]/[~]/[ ]` tri-state is never explained (clean.go:881–900).

### The non-TTY / flag branch is full of traps
- **Piped without `--yes`**: prints "Review — these exact commands **will
  run**", then refuses with exit 2 (clean.go:115–125). The sentence is false,
  the exit code is the same as a typo'd flag, and the 14–47 s scan is thrown
  away — re-running with `--yes` scans again from zero.
- `--json` (non-dry-run, no `--yes`) hits the same refusal, and the hint says
  "pass --yes or --dry-run" with no mention that `--json` alone can print the
  plan (clean.go:120–125). A script author's first contact with the tool is a
  dead end.
- `--plain` is silently ignored by analyze (analyze.go:89 checks only JSON +
  TTY).
- `--dry-run --yes`: dry-run silently wins, `--yes` is a no-op with no notice.
- `--yes` on a TTY skips the TUI entirely with zero pause between preview and
  execution (clean.go:115–135).
- clean decides interactivity from stdout only (clean.go:96) while the
  whitelist manager checks stdin *and* stdout (clean.go:190) — two TTY
  philosophies in one package.
- Quitting a TUI with Ctrl-C exits 0; interrupting during Execute exits 130.
  Scripts can't tell them apart.

## C. Surface noise (things in the product that do nothing)

Verified, each with evidence:

1. **`--log-level`, `-v/--verbose`, `--quiet` are dead flags.** Declared at
   cli/root.go:106–108; a grep for readers of `Flags.LogLevel/Verbose/Quiet`
   finds only the declarations. They appear in every `--help` and do nothing.
   Relatedly, logging is effectively absent app-wide: `owner.Runner.Log`
   (owner/runner.go:42) is never assigned in production, and
   `general.log_level` feeds nothing.
2. **`purge` is a deprecated alias that owns the only `--age` flag.**
   `burrow purge --only dev` silently clobbers the user's `--only`
   (cli/purge.go:54). The age knob for the Projects category exists *only* on
   the deprecated command; the modern path (`clean --only projects`) has no
   `--age`, and the documented way to set project roots is `BURROW_PURGE_PATHS`
   for a command the README calls deprecated.
3. **`--min-size 0` cannot turn config off**: the resolver treats the literal
   `"0"` (the flag's own default) as "unset, use config" (clean.go:267–274).
4. **`-x/--one-file-system` help says "(default)" but the flag default is
   false** (analyze.go:71); the real default is config (analyze.go:64), and
   `--cross-mounts` vs `-x` is resolved by cobra `Changed()` inspection
   (analyze.go:58–65) — two flags, one bool, invisible precedence.
5. **clean-only globals parse on every command**: `--only`, `--exclude`,
   `--min-size`, `--no-owner` are persistent (root.go:95–108), so
   `burrow analyze --min-size 1G` or `burrow history --only dev` succeed and
   do nothing.
6. **`--no-color` duplicates `--color=never`** (root.go:103–104) and beats
   `--color=always` by evaluation order (analyze.go:253–271).
7. **`docs` and cobra's `completion` ship in the user's command menu**
   (root.go:110–118) — packager tools in the product surface.
8. **`history` prints an 8-char run id (`shortID`, history.go:123–127) but
   `--restore` requires the full exact id** (journal/history.go:66–73). The
   table advertises an id that fails when you paste it. Either accept prefixes
   or print full ids.
9. **Three JSON styles**: pretty JSON on clean/analyze/config, compact JSONL on
   history (history.go:58–63), one-line on version (version.go:17).
10. **Summary/preview alignment mismatch**: the preview width-aligns globally
    (tui/clean.go:262–268) but `RenderSummary` hardcodes `%-28s` (clean.go:148)
    — one long display name desyncs the table. `Selected:` also prints twice
    in `--plain` mode (clean.go:80 and :141).
11. Exit-code seams: root-without-SUDO_USER refuses with exit 1 (a usage error
    wearing a generic code, owner/user.go:50); guard-stopped runs exit 75
    while the stdout summary says only `ok/skipped/failed` — nothing on stdout
    explains the 75 (clean.go:315–327); nonexistent `--run` id exits 1,
    missing `--run` exits 2.

## D. The product story vs "help me understand my storage"

This is the Mole comparison the owner actually cares about. Mole is
`uninstall / clean / analyze / doctor`, one command each, beautiful one-shot
output. burrow's honest read:

**What burrow has that Mole doesn't:** journaled undo (`history --restore`),
per-item recovery contracts, hardlink/reflink-correct sizing, a real safety
model. That's the differentiator; keep it.

**Where the storage *understanding* story underdelivers:**
- No totals-first screen. The first thing a user sees is a tree of checkboxes,
  not "you have 1.9 TiB used; ~350 GiB looks reclaimable; here's the shape of
  it." The README's pitch is a grouped review screen, and even that screen
  leads with per-group noise instead of the one number.
- The headline number on the clean screen is arguably wrong: a category header
  showing "User cache 239.0 GiB" (everything present) next to "Selected: 6.5
  GiB" (everything actionable) trains the user to distrust the sizes. One
  "reclaimable now" total at top, details below.
- **Nothing explains why rows are off.** "cheap,active", "expensive", "med"
  appear as bare columns. Mole-style polish would be one sentence per
  group ("dev caches are never pre-selected — press `a` to override") — the
  mechanism half-exists as `PreviewNote()` but only one category uses it.
- **analyze is a dead end by design.** No delete keys (right), but also no
  "this looks like a projects/cache directory — run burrow clean" hop (the
  dead `[R]` marker, section B), no largest-files flat view in the TUI (the
  JSON has one), no mtime column, no percentages. The core loop — spot big
  thing, understand it, reclaim it — requires leaving the app.
- **No trends or history-of-space.** "Storage patterns" would mean
  cheaply journaling df snapshots per run and offering `burrow analyze
  --since`, even just "last month +120 GiB, mostly ~/Projects". The journal
  already writes per run; the data for a basic version mostly exists.
- **No doctor equivalent.** A health check (full `/tmp`, huge journald, stale
  kernels, broken symlinks, near-full partitions) is Mole's most
  self-explanatory feature; burrow declares "not a system optimizer"
  (README.md:282) and skips it entirely.
- **No uninstall.** burrow removes unused flatpaks/disabled snaps but cannot
  uninstall an app with its leftovers — Mole's flagship.
- **Non-TTY output is a deliberate stub.** The plain path ends in "… +265 more
  (use --json for the full list)" (clean preview) where Mole's signature is a
  complete, pretty terminal summary. `RenderSummary` is close to that; it just
  isn't the preview.

**Breadth honesty:** the README's category tour implies full support
everywhere, but mutating system rows only exist for apt and dnf;
pacman/zypper/apk are detection stubs (distro/distro.go:3, 116–126) and the
container matrix covers only ubuntu/debian/fedora.

## E. Internal cruft (code that is fossilized, duplicated, or misleading)

### E4. Correctness nits found in passing
- `config.FormatBytes` **panics for n ≥ 1 PiB**: `"KMGT"[exp]` indexes past
  the string (units.go:87; exp maxes at 3). One-byte fix (`"KMGTPE"[exp]` +
  the loop's practical ceiling, or an if).
- `TrashAction.Run` accepts a ctx and ignores it (action/action.go:108); the
  cross-device trash fallback (trash/trash.go:244–299) has **no timeout and no
  cancellation** — trashing a multi-GB dir across filesystems during Execute is
  uncancellable except at the next item boundary (pipeline.go:344).
- `EmptyTrashAction` declares `RecoveryOwner` (action/emptytrash.go:24) to fit
  the two-contract model — a permanent hand-mutation journaling as
  `action: "owner", argv: nil`. Defensible, but the action.go:4 comment "there
  is no permanent-delete primitive" and README.md:19–20 "no permanent-delete
  primitive in the binary" are now technically false in spirit; emptying the
  trash is exactly that, under a label.
- `projects.Category` stores warnings in the category struct during Discover
  (projects.go:58–60) — mutable state on a value registered as a singleton.
- gdu is confined to one file as promised, but the "shell-out fallback to
  `gdu --json`" that AGENTS.md relies on **has never been written** — what
  exists is a `du -sk` repair path (scan.go:278–336).
- Dev-caches `CacheRoots` (dev.go:162–175) is a second manual list mirroring
  the item builders; add a dev cache without updating it and user-cache
  double-lists the same bytes.

### E5. Shape
- Adding a category costs a new package + ~50 lines of ID/Title/PreviewNote
  boilerplate + a registry line + a `DefaultCategories` default + README
  (seven places).
- `Reconciler` and `Warner` catalog hooks each have exactly one implementer
  and are wired in the CLI by type assertion (cli/clean.go:152–164), not by
  the engine — conceptually planning steps, living as CLI trivia.
- `internal/purge` (3 files, ~500 non-test lines) has exactly one consumer,
  `catalog/projects` — the package boundary is now pure indirection.
- `dev.go` hand-codes ~25 near-identical trash-item builders (dev.go:241–417)
  where one data table + the ~8 owner-command exceptions would halve the file.
- Test coverage shape: strong in safe/purge/scan/distro/config/trash; **weak
  in `owner/commands_test.go` — 2 tests guarding a 474-line allow-list table**
  (the argv tables are the product's blast radius and are exercised only
  indirectly), thin in `system/parsers_test.go` (one 10-line test against four
  parser sites) and `engine/env_test.go` (2 tests). `safety_test.go` imports
  `internal/cli` for `ExitCode` — inverted layering.

discipline, gdu containment, and the fail-closed posture are better than

unified interaction, and truth-in-documentation — none of it architectural.
